# TTS 文本前处理 v3

## 1. 问题定位

旧服务使用 `model_app/text_routing.py` 中的保守替换规则，只覆盖部分电力单位、罗马数字、字母缩写和小数。传统时间 `8：35` 没有进入“时刻”规则，后续仅按普通冒号处理，因此模型漏读了时间语义。

附件中的 `power_normalizer.py` 已覆盖大量电力调度格式，但其说明中约定日期、时钟由另一个通用模块处理；实际直接运行会把 `8：35` 转成“八比三十五”。因此不能原样替换，需要先补齐通用原子规则。

## 2. 当前处理顺序

1. HTML 实体、零宽字符、全角数字/字母和空白清理；
2. 优先识别并保护日期、时刻、时刻范围、电话和交直流电压；
3. 处理标准编号、设备编号、参数、范围、单位、百分比和特殊符号；
4. 处理比例、正负号、数学关系及剩余数字；
5. 恢复保护片段，再做轻量空白整理；
6. 纯英文句子保持原样，避免英文数字被中文规则改写。

关键实现：

| 文件 | 作用 |
| --- | --- |
| `model_app/power_normalizer.py` | 通用中文规则 + 电力领域规则 |
| `model_app/text_routing.py` | 中英文语境选择、音色路由、服务兼容入口 |
| `tests/test_power_normalizer.py` | 时间、日期、单位、编号和英文边界回归 |
| `bench/normalizer_bench.py` | 预处理微基准与 API RTF 对比 |

## 4. RTF 影响

测试环境：现网 `sherpa-tts` CPU 容器，304 次预热后取 300 次测量的中位数。

| 文本 | 字符数 | 预处理 p50 | p95 |
| --- | ---: | ---: | ---: |
| `8：35` | 4 | 0.048 ms | 0.052 ms |
| 电力告警混合样本 | 137 | 0.656 ms | 0.717 ms |
| 同一告警重复 20 次 | 2740 | 13.283 ms | 13.668 ms |

同一 137 字告警通过 `/api/tts` 交替请求 9 次：

| 输入方式 | 总耗时中位数 | 音频时长中位数 | RTF |
| --- | ---: | ---: | ---: |
| 原始文本 | 0.8397 s | 31.097 s | 0.02700 |
| 预先规范化文本 | 0.8264 s | 31.054 s | 0.02661 |

结论：

- 前处理直接增加的 CPU 时间约为 `0.66 ms/137 字`，相对约 `0.83 s` 的请求耗时不到 `0.1%`。
- RTF 主要由 ONNX 模型、分块数量和 CPU 并发决定；规范化本身不会改变模型采样或声码器路径。
- 规范化会改变送入模型的文本、音素和音频时长，因此 RTF 可能出现小幅波动，但不是推理框架层面的直接开销。
- 前处理在事件循环内同步执行；按当前中位耗时估算，100 QPS、每请求 137 字时约占单核 7%，部署高并发前仍应纳入容量评估。

复测命令：

```bash
python bench/normalizer_bench.py \
  --iterations 300 \
  --api-url http://127.0.0.1:8000/api/tts \
  --repeats 9
```
